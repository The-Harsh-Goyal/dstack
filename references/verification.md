# Verification: the output verification workflow

Some native design-agent environments (such as Claude.ai Artifacts) have a built-in `fork_verifier_agent` that spins up a subagent to check iframe screenshots. Most agent environments (Claude Code / Codex / Cursor / Trae / etc.) don't have this built in; doing it manually with Playwright covers the same verification scenarios.

## 🔴 Rule 0: verify your verification tools first

**Before you trust any render result, first confirm that the renderer itself renders correctly.** This comes before all other verification,
because when the tool can't be trusted, every later step gives you a false green light.

Two real failures (2026-09, a PPTX delivery built on a client template):

- **Thumbnails generated by macOS `qlmanage -t` let through 4 bugs that caused overlapping text**. It uses a simplified
  render path and is far more forgiving about line spacing than real PowerPoint. All 20 slides looked right one by one, but the moment the user opened it in WPS
  the text was piled on top of text. **A thumbnail is not a render; don't use it as acceptance evidence.**
- **LibreOffice on macOS renders Chinese PPTX as nothing but tofu boxes**, which for a while made it look like the file was broken.

**How to tell whether it's a tool problem or an output problem: run a control experiment.**
Give the same renderer **a file of the same kind that's known to be correct**. In the second case above, rendering the client's original official template
made its Chinese disappear entirely too, which settled on the spot that it was an environment problem, not a problem with your file.
This step can save hours of debugging in the wrong direction.

**Trustworthiness ranking (macOS)**:

| Tool | Can you trust it |
|---|---|
| `qlmanage -t` thumbnails | ❌ Not usable as acceptance evidence |
| LibreOffice headless | ⚠️ Layout is trustworthy; fonts/Chinese may be lost entirely |
| Keynote + AppleScript export to PDF | ✅ Top choice for automation, a real layout engine |
| Opening in the target software itself (PowerPoint / WPS) | ✅ Final confirmation, checked by a human |

⚠️ **Don't use System Events to inject keystrokes** to drive the GUI for paging and screenshots: the keystrokes will land in whatever window the user is currently
typing in. Either use AppleScript's document-level API (such as Keynote's `export`), or have a human look.

**Add a mechanical check that doesn't depend on any renderer**: character-by-character text comparison (source data vs output,
must be exactly equal after `re.sub(r'\s+','')`), and per-slide element count comparison. A renderer can fool your eyes, but not a count.

## Verification checklist

Every time you produce HTML, go through this checklist:

### 1. Browser render check (mandatory)

The most basic: **does the HTML open at all**? On macOS:

```bash
open -a "Google Chrome" "/path/to/your/design.html"
```

Or take a Playwright screenshot (next section).

### 2. Console error check

The most common problem in HTML files is a JS error causing a blank page. Run it through Playwright:

```bash
python3 /workspace/dstack/scripts/verify.py path/to/design.html
```

This script will:
1. Open the HTML in headless chromium
2. Save a screenshot to the project directory
3. Capture console errors
4. Report status

See `scripts/verify.py` for details.

### 3. Multi-viewport check

For responsive designs, capture multiple viewports:

```bash
python verify.py design.html --viewports 1920x1080,1440x900,768x1024,375x667
```

### 4. Interaction check

Tweaks, animations, button toggles: default static screenshots can't see them. **We recommend having the user open a browser and click through it themselves**, or record the screen with Playwright:

```python
page.video.record('interaction.mp4')
```

### 5. Slide-by-slide check

For deck-type HTML, capture slide by slide:

```bash
python verify.py deck.html --slides 10  # capture the first 10 slides
```

This generates `deck-slide-01.png`, `deck-slide-02.png`... for quick browsing.

## Playwright Setup

One-time setup, all local to the dstack root (no global installs; on Harsh's box it is already done,
check with `bash /workspace/dstack/tools/doctor.sh`):

```bash
cd /workspace/dstack
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt   # Python: playwright, pillow, python-pptx, pytest
npm ci                                                               # Node: playwright, pdf-lib, pptxgenjs, sharp
.venv/bin/python -m playwright install chromium                      # only if doctor.sh says Chromium is missing
```

Then run Python scripts with `/workspace/dstack/.venv/bin/python`; Node scripts find the local `node_modules` on their own.

## Screenshot best practices

### Capture the full page

```python
page.screenshot(path='full.png', full_page=True)
```

### Capture the viewport

```python
page.screenshot(path='viewport.png')  # captures only the visible area by default
```

### Capture a specific element

```python
element = page.query_selector('.hero-section')
element.screenshot(path='hero.png')
```

### High-resolution screenshots

```python
page = browser.new_page(device_scale_factor=2)  # retina
```

### Wait for animations to finish before capturing

```python
page.wait_for_timeout(2000)  # wait 2 seconds for animations to settle
page.screenshot(...)
```

## Sending screenshots to the user

### Open local screenshots directly

```bash
open screenshot.png
```

The user will look at it in their own Preview/Figma/VSCode/browser.

### Upload to an image host and share a link

If remote collaborators need to see it (for example on Slack/Feishu/WeChat), have the user upload the screenshot with their own image-hosting tool or an MCP to get a permanent link they can paste anywhere.

## When verification fails

### Blank page

There's definitely an error in the console. Check first:

1. Whether the integrity hashes on the React+Babel script tags are right (see `react-setup.md`)
2. Whether it's a `const styles = {...}` naming conflict
3. Whether cross-file components were exported to `window`
4. JSX syntax errors (babel.min.js doesn't report them; switch to the unminified babel.js)

### Janky animation

- Record a stretch in the Chrome DevTools Performance tab
- Look for layout thrashing (frequent reflows)
- Prefer `transform` and `opacity` for motion (GPU accelerated)

### Wrong fonts

- Check whether the `@font-face` url is reachable
- Check the fallback fonts
- Chinese fonts load slowly: show the fallback first, then switch once loaded

### Misaligned layout

- Check that `box-sizing: border-box` is applied globally
- Check the `*  margin: 0; padding: 0` reset
- Turn on gridlines in Chrome DevTools to see the actual layout

## Verification = the designer's second pair of eyes

**Always go through it yourself**. When AI writes code, these come up often:

- Looks right but the interaction has bugs
- Static screenshot is fine but things shift on scroll
- Looks good on wide screens but breaks on narrow ones
- Forgot to test dark mode
- Some components don't respond after switching Tweaks

**One minute of verification at the end can save an hour of rework**.

## Common verification script commands

```bash
# basic: open + screenshot + capture errors
python verify.py design.html

# multiple viewports
python verify.py design.html --viewports 1920x1080,375x667

# multiple slides
python verify.py deck.html --slides 10

# output to a specific directory
python verify.py design.html --output ./screenshots/

# headless=false, opens a real browser for you to watch
python verify.py design.html --show
```

## Hard checks on video output (verify-video.sh)

Rendered MP4s / finished films aren't passed by eye; use the script for hard checks (checks on the HTML composition side are handled by the `hyperframes check` five-gate audit; this script only covers the output side):

```bash
# finished film (audio track required by default)
bash scripts/verify-video.sh final.mp4 --duration=22 --fps=60 --width=1920 --height=1080

# silent intermediate output
bash scripts/verify-video.sh raw.mp4 --duration=10 --fps=60 --no-audio

# cinematic style that deliberately opens on black
bash scripts/verify-video.sh film.mp4 --duration=30 --fps=60 --allow-black-open
```

What it checks: resolution/frame rate, duration error (±2%), audio stream presence (machine enforcement of the iron rule that no audio track = half-finished), black frames at start and end (blackdetect, the typical symptom of a recording start offset / loop jump-back), and LUFS loudness (finished-film target -14±4). If the exit code isn't 0, you may not deliver.
